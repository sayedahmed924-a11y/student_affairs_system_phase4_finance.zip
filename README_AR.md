# نظام شؤون الطلاب - الإصدار التأسيسي

نظام ويب عربي متعدد المستخدمين للعمل داخل شبكة LAN دون اتصال بالإنترنت بعد تجهيز ملفات التشغيل محليًا.

## المتطلبات
- جهاز خادم داخل الشبكة المحلية بنظام Windows 10/11 أو Linux.
- Docker Desktop مع Docker Compose (أو تشغيل Python/PostgreSQL يدويًا).
- أجهزة الموظفين تستخدم المتصفح للوصول إلى عنوان الخادم على المنفذ 8000.

> ملاحظة: يجب تنزيل صور Docker وحزم Python أثناء تجهيز الخادم أول مرة، أو نقلها إليه من وسيط خارجي. التشغيل اليومي لا يحتاج إنترنت.

## التشغيل باستخدام Docker
1. انسخ المجلد إلى جهاز الخادم.
2. انسخ `.env.example` إلى ملف باسم `.env` وعدّل كلمات المرور و`SECRET_KEY`، واستبدل `192.168.1.10` بعنوان IP الفعلي الثابت لجهاز الخادم (لا تكتب نطاق الشبكة بصيغة CIDR).
3. شغّل:
   `docker compose up -d --build`
4. ينشئ تشغيل الحاوية الجداول ويطبق ملفات الترحيل باستخدام `migrate --fake-initial`؛ وهذا يدعم قاعدة البيانات القديمة التي أُنشئت بالإصدار التأسيسي ثم يضيف حقول إعدادات التقدير الجديدة.
5. أنشئ مدير النظام:
   `docker compose exec web python manage.py createsuperuser`
6. افتح من جهاز الخادم: `http://127.0.0.1:8000`
7. افتح من أجهزة الشبكة: `http://IP-OF-SERVER:8000`

## الصلاحيات
من لوحة الإدارة `/admin/` أنشئ مجموعات مثل:
- موظف استعلامات: `view_student`
- موظف تسجيل: `view_student`, `add_student`
- موظف تعديل: `view_student`, `change_student`
- مدير شؤون الطلاب: صلاحيات الاعتماد ومراجعة السجلات

أنشئ المستخدمين وأضفهم للمجموعات. لا تستخدم حساب المدير اليومي للموظفين.

## قالب Excel
يجب أن يكون الملف XLSX والصف الأول أسماء الأعمدة التالية:
- إلزامي: `university_id`, `full_name`
- اختياري: `national_id`, `nationality`, `phone`, `address`, `academic_year`, `department`, `division`, `study_status`, `notes`

القيمة المقبولة لـ `study_status`: `new`, `continuing`, `graduated`, `withdrawn`, `dismissed`, `suspended`.

الاستيراد ينشئ معاينة قبل الاعتماد ويطابق الطالب بالرقم الجامعي.

## الوضع الحالي وحدود الإصدار التأسيسي
هذه بداية تنفيذية تشمل إدارة الطلاب، تسجيل التعديلات، معاينة Excel، الاعتماد، وتسجيل الدخول والصلاحيات الأساسية، بالإضافة إلى نموذج أكاديمي للفصول والمواد وقيود الطلاب وتسجيل المواد والنتائج والوقائع الأكاديمية. وحدات المواد والنتائج والرسوم والقرارات والمستندات الأكاديمية المتخصصة، والاستعادة التفصيلية لنسخة حقل بعينه، وتقارير PDF/Excel، وشاشة إدارة الصلاحيات المخصصة ما زالت مراحل تطوير لاحقة.

قبل الاستخدام الفعلي يجب اختبار النسخ الاحتياطي والاستعادة، إعداد HTTPS إن كانت الشبكة تتطلبه، تقييد الوصول من جدار الحماية على شبكة المؤسسة، مراجعة الصلاحيات، وإضافة سياسات الاحتفاظ بالبيانات. سجل التدقيق داخل التطبيق لا يغني عن النسخ الاحتياطي وسجلات الخادم.


## الوحدة الأكاديمية المضافة
تتضمن قاعدة البيانات الآن:
- `AcademicTerm`: العام الجامعي والفصل الدراسي وتواريخه.
- `Course`: كود المادة واسمها والقسم والفرقة والساعات المعتمدة.
- `StudentEnrollment`: قيد الطالب في فصل دراسي، مع منع تكرار قيده في الفصل نفسه.
- `CourseRegistration`: تسجيل مادة للطالب ودرجات أعمال السنة والامتحان والمجموع والتقدير والحالة.
- `StudentAcademicEvent`: إنذارات ورسوب وانسحاب وإعادة قيد وتحويل وقرارات مع المستند والسند.

من واجهة «الشؤون الأكاديمية» يمكن إدارة الفصول والمواد وقيود الطلاب والنتائج والوقائع. ويمكن أيضًا إدارة البيانات الأكاديمية من لوحة `/admin/` وفق الصلاحيات. تغييرات النتائج من لوحة الإدارة تسجل في سجل التعديلات.


## المرحلة الأكاديمية الثالثة

أضيفت وظائف تشغيلية جديدة:

- عند تسجيل قيد طالب في فصل دراسي، تُضاف تلقائيًا المواد النشطة المطابقة للفرقة والقسم. المادة التي لا تحدد قسمًا أو فرقة تعتبر عامة.
- عند إضافة مادة جديدة، تُربط تلقائيًا بقيود الطلاب المطابقة الموجودة بالفعل.
- لكل مادة إعدادات مستقلة للنهاية العظمى ودرجة النجاح وحدود التقديرات (ممتاز، جيد جدًا، جيد). الحدود الافتراضية 85% و75% و65%، ويمكن تعديلها من بيانات المادة وفق لائحة الكلية.
- عند إدخال أعمال السنة والامتحان، يحسب النظام المجموع والنسبة والتقدير وحالة النجاح أو الرسوب تلقائيًا. لا تُعتمد نتيجة نهائية إذا كانت إحدى الدرجتين ناقصة، أو إذا تجاوز المجموع النهاية العظمى.
- إعادة القيد تنشئ قيدًا جديدًا في فصل جديد، وتسجل واقعة إعادة قيد، ولا تحذف القيود أو النتائج السابقة.
- كشف درجات الطالب يعرض المواد والنتائج لكل فصل، ويحسب الساعات المجتازة والمتبقية وفق المواد النشطة المسجلة في كتالوج المواد، مع زر طباعة من المتصفح.

**تنبيه بخصوص الساعات المتبقية:** الحساب الحالي يعتمد على مجموع الساعات للمواد النشطة المعرفة في كتالوج المواد للقسم (والمواد العامة). يجب استكمال كتالوج جميع مواد الخطة بدقة قبل الاعتماد على الرقم رسميًا. لم يتم افتراض إجمالي ساعات برنامج ثابت.

**تنبيه بخصوص التقديرات:** حدود التقديرات قابلة للتعديل لكل مادة؛ راجع لائحة المؤسسة قبل التشغيل الرسمي واضبطها وفق نظامها المعتمد.

## المرحلة الرابعة: الإدارة المالية

أضيفت وحدة مالية داخل النظام تشمل:

- تسجيل استحقاق مالي على طالب وربطه اختياريًا بالفصل الدراسي.
- تسجيل دفعات جزئية أو كاملة مع رقم إيصال فريد وطريقة الدفع والرقم المرجعي.
- منع تجاوز قيمة السداد للرصيد المتبقي، مع قفل سجل الاستحقاق أثناء تسجيل الدفعة لتقليل تعارض الموظفين المتزامنين.
- احتساب إجمالي المطلوب والمحصل والمتبقي وحالة كل استحقاق.
- البحث في الاستحقاقات والإيصالات بالرقم الجامعي أو اسم الطالب أو رقم الإيصال.
- عرض وطباعة إيصال السداد.
- إلغاء الإيصال بسبب موثق بدل حذفه، مع الاحتفاظ باسم الموظف ووقت الإلغاء.
- إلغاء الاستحقاق فقط إذا لم توجد عليه دفعات فعالة، مع حفظ سبب الإلغاء.
- منع الإضافة أو التعديل أو الحذف المباشر للإيصالات والاستحقاقات من Django Admin؛ تتم العمليات من شاشات النظام.

### صلاحيات الوحدة المالية

يستخدم النظام صلاحيات Django القياسية التي تُنشأ تلقائيًا للموديلات الجديدة:

- `students.add_studentcharge`: إضافة استحقاق.
- `students.view_studentcharge`: عرض الاستحقاقات.
- `students.change_studentcharge`: إلغاء استحقاق.
- `students.add_paymentreceipt`: تسجيل سداد.
- `students.view_paymentreceipt`: عرض الإيصالات.
- `students.change_paymentreceipt`: إلغاء إيصال.

يجب على مدير النظام توزيع هذه الصلاحيات على مجموعات الموظفين من لوحة الإدارة قبل التشغيل الفعلي. شاشة المالية متاحة للمستخدمين المسجلين، أما عمليات الإضافة والإلغاء فتحميها الصلاحيات المحددة أعلاه.

### تحديث قاعدة البيانات

بعد استبدال ملفات الإصدار السابق، خذ نسخة احتياطية من قاعدة البيانات ثم نفّذ:

```bash
docker compose up -d --build
```

سيطبق Django ملف الترحيل `0003_finance_module` تلقائيًا عند بدء الخدمة.

**تنبيه محاسبي:** هذه وحدة تحصيل واستحقاقات تأسيسية وليست بديلًا عن نظام محاسبي قانوني أو دفتر أستاذ عام. قبل الاستخدام الرسمي، يجب اعتماد دورة المستندات والترقيم وسياسات الإلغاء والمراجعة من الإدارة المالية، وتجربة حالات السداد المتزامن والاسترداد على نسخة اختبارية.


## المرحلة الخامسة: التقارير ولوحة المتابعة

أضيفت إلى وحدة التقارير والواجهة الرئيسية الوظائف التالية:

- تقرير بيانات الطلاب، وتقارير القيود الدراسية حسب العام والفصل والقسم والفرقة.
- تقرير الدرجات والنتائج، وتقرير إحصائي للنجاح والرسوب ونسبة النجاح حسب المادة.
- تقرير الرسوم والتحصيل والمتأخرات مع إجمالي المستحق والمحصل والمتبقي.
- البحث داخل التقارير باستخدام الرقم الجامعي، مع تصدير النتائج إلى Excel والطباعة أو الحفظ PDF من المتصفح.
- رسم بياني مبسط في لوحة التحكم لتوزيع الطلاب حسب الحالة الدراسية.
- تقرير شامل للطالب يجمع بياناته وقيوده ونتائجه ووقائعه الأكاديمية وملخص استحقاقاته.
- كشف حساب مالي للطالب يعرض الاستحقاقات والدفعات الفعالة والرصيد الجاري، مع استبعاد الإيصالات الملغاة والاستحقاقات الملغاة.

يمكن فتح التقرير الشامل وكشف الحساب المالي من ملف الطالب، كما يمكن فتح التقارير العامة من لوحة التحكم.

**تنبيه تشغيلي:** التعديلات البرمجية لا تعني اعتماد التقارير محاسبيًا أو أكاديميًا تلقائيًا. يجب اختبارها على نسخة من قاعدة البيانات والتحقق من صحة البيانات واللوائح قبل الاستخدام الرسمي. لا تُجرِ ترحيلات قاعدة البيانات في هذه الإضافات لأنها لا تضيف حقولًا أو جداول جديدة.

## المرحلة السادسة: حسابات الموظفين والصلاحيات

تعتمد إدارة الوصول على مجموعات وصلاحيات Django الأصلية؛ لا توجد جداول مخصصة جديدة لهذه المرحلة ولا حاجة إلى migrations إضافية إذا كانت قاعدة بيانات النظام مهيأة أصلًا.

### الوصول إلى شاشة الإدارة
- سجّل الدخول بحساب مدير النظام (Superuser).
- افتح المسار: /students/staff-access/.
- عند أول فتح للشاشة تُنشأ مجموعات الأدوار المحددة وتُضبط صلاحياتها تلقائيًا.
- أنشئ حساب الموظف، وحدد كلمة المرور وحالة الحساب، ثم اختر مجموعة أو أكثر من مجموعات الصلاحيات.
- لتجميد موظف، أزل علامة «الحساب نشط» واحفظ.

### الأدوار الجاهزة
- **مدير شؤون الطلاب:** صلاحيات تشغيلية واسعة تشمل التسجيل والأكاديمية والمالية والتقارير.
- **شؤون التسجيل:** ملفات الطلاب والتسجيل والاستيراد وسجل التعديلات دون رصد النتائج أو تنفيذ التحصيل.
- **الشؤون الأكاديمية:** القيود والمواد ورصد النتائج والوقائع الأكاديمية.
- **الإدارة المالية:** الاستحقاقات والتحصيل والإيصالات والتقارير المالية.
- **مراجع التقارير:** الاطلاع على بيانات التقارير دون تعديل السجلات.
- **استعلام فقط:** قراءة البيانات المسموح بها دون إضافة أو تعديل.

يمكن إسناد أكثر من دور إلى الموظف عند الحاجة. لا تمنح الأدوار صلاحية دخول لوحة Django الإدارية؛ حسابات الموظفين تُنشأ بقيمة is_staff=False. تبقى إدارة حسابات الموظفين حصرًا على حسابات Superuser.

### الحماية المطبقة
- التحقق من الصلاحية على مستوى الـ view وليس إخفاء الروابط فقط.
- منع فتح كشف الدرجات دون صلاحية عرض النتائج.
- منع فتح كشف الحساب المالي دون صلاحية عرض الاستحقاقات والإيصالات.
- حصر شاشة إدارة الموظفين في مدير النظام.
- تسجيل إنشاء وتعديل حسابات الموظفين في سجل Django الإداري.
- إخفاء روابط الوظائف التي لا يملك المستخدم صلاحيتها.

### ملاحظات تشغيلية
- يجب أن تكون migrations الأساسية لـ Django وطلاب النظام مطبقة مسبقًا حتى تكون صلاحيات النماذج الافتراضية متاحة.
- أنشئ أول حساب Superuser من بيئة الخادم باستخدام الأمر python manage.py createsuperuser إذا لم يكن موجودًا.
- لا تستخدم حساب Superuser في العمل اليومي؛ أنشئ حسابًا منفصلًا لكل موظف.
- اختبر كل دور بحساب مستقل قبل تشغيل النظام على شبكة LAN، خصوصًا صفحات التقارير والطباعة والإيصالات.

- أضيفت صلاحيتان منفصلتان للتصدير والطباعة: export_reports و print_reports. تُنشآن تلقائيًا ضمن صلاحيات Django عند فتح شاشة إدارة الموظفين، وتُمنحان لأدوار الإدارة المالية ومراجع التقارير ومدير شؤون الطلاب فقط.
- تنزيل Excel محمي بفحص صلاحية على الخادم، كما أن فتح صفحة طباعة الإيصال محمي بصلاحية مستقلة. أزرار الطباعة في صفحات التقارير وكشوف الطلاب لا تظهر إلا للمصرح لهم.
- تنبيه: لا يستطيع تطبيق ويب منع المستخدم منعًا تقنيًا كاملًا من استخدام أدوات المتصفح مثل Ctrl+P أو تصوير الشاشة بعد السماح له بعرض البيانات؛ صلاحية الطباعة تتحكم في وظائف الطباعة التي يوفرها النظام نفسه.

### اختبار المرحلة السادسة
بعد إعداد قاعدة البيانات وتشغيل migrations الأساسية، نفّذ:
python manage.py test students

تتضمن الاختبارات التحقق من إنشاء مجموعات الأدوار وصلاحيات التصدير والطباعة، وأن شاشة إدارة الموظفين لا تسمح بالدخول إلا لمدير النظام.

## المرحلة السابعة: النسخ الاحتياطي والاستعادة

أضيفت آلية نسخ احتياطي مستقلة عن قاعدة البيانات وخدمة الويب، وتدعم PostgreSQL (صيغة dump المخصصة) وSQLite (نسخة متسقة باستخدام SQLite backup API)، كما تحفظ ملفات المستندات المرفوعة من مجلد media في أرشيف مستقل مرتبط بكل نسخة قاعدة بيانات.

### النسخ التلقائي
- خدمة Docker باسم backup تنشئ نسخة عند بدء الخدمة، ثم تكرر النسخ كل 24 ساعة افتراضيًا.
- تحفظ النسخ في وحدة Docker مستقلة باسم backup_data، ومجلدها داخل الحاويات /app/backups.
- تتكون كل نقطة استعادة من ملف قاعدة البيانات (.dump أو .sqlite3) وملف مستندات مطابق باللاحقة _media.tar.gz؛ يجب الاحتفاظ بالملفين معًا.
- يتحقق النظام من سلامة النسخة بعد إنشائها: فحص أرشيف PostgreSQL أو PRAGMA integrity_check في SQLite.
- يحتفظ النظام بالنسخ لمدة 30 يومًا افتراضيًا ويحذف الأقدم تلقائيًا.
- يمكن تغيير المدة والفاصل الزمني من ملف .env باستخدام BACKUP_RETENTION_DAYS=30 وBACKUP_INTERVAL_SECONDS=86400 وBACKUP_DIR=/app/backups.

### النسخ اليدوي والتنزيل
- سجّل الدخول بحساب Superuser.
- افتح /students/backups/.
- اضغط «إنشاء نسخة احتياطية الآن».
- تظهر ملفات قاعدة البيانات وملفات المستندات المرفوعة مع الحجم والتاريخ. نزّل الملفين المتطابقين معًا عند حفظ نسخة خارج الخادم.
- شاشة النسخ الاحتياطي وتنزيل الملفات محمية بحساب مدير النظام فقط.

### الاستعادة
الاستعادة عملية تستبدل بيانات قاعدة البيانات؛ لذلك لا توجد استعادة مباشرة من المتصفح. يجب أولًا إيقاف خدمة الويب لمنع الكتابة أثناء الاستعادة، ثم تنفيذ الأوامر من مجلد المشروع:

    docker compose stop web backup
    docker compose run --rm --no-deps web python manage.py restore_database student_affairs_YYYYMMDD_HHMMSS.dump --confirm RESTORE
    docker compose up -d web backup

لنسخة SQLite استخدم اسم الملف ذي الامتداد .sqlite3 بدل .dump. يجب أن يكون ملف أرشيف media المطابق موجودًا بجوار ملف قاعدة البيانات. ينشئ أمر الاستعادة نسخة أمان إضافية من قاعدة البيانات وملفات media الحالية قبل الاستبدال، ويتحقق من مسارات الأرشيف لمنع الكتابة خارج مجلد media. في PostgreSQL تتم الاستعادة داخل معاملة واحدة مع إيقاف العملية عند أول خطأ.

### حماية إضافية وإجراءات موصى بها
- لا تضع ملفات النسخ في Git ولا داخل مجلد static أو media.
- احتفظ بنسخة ثانية خارج جهاز الخادم (قرص خارجي أو جهاز تخزين آخر)؛ وحدة Docker وحدها لا تحمي من تلف القرص أو فقد الجهاز.
- اختبر الاستعادة دوريًا على قاعدة اختبارية، وتحقق من أعداد الطلاب والقيود والنتائج والإيصالات قبل إعادة فتح النظام.
- لا تُجرِ الاستعادة أثناء عمل الموظفين.
- بعد تحديث ملفات المشروع، أعد بناء الخدمات: docker compose up -d --build.
- في التشغيل دون إنترنت، جهّز مسبقًا صورة Docker والحزم المطلوبة، بما فيها postgresql-client-16، على جهاز الخادم.

**مهم:** خدمة النسخ التلقائي تبدأ بعد جاهزية خدمة الويب وقاعدة البيانات. توقيت النسخ كل 24 ساعة محسوب من بدء خدمة backup وليس موعدًا ثابتًا من اليوم. تنزيل نسخة احتياطية إلى جهاز آخر خطوة مهمة لتأمين نسخة خارج الخادم.

## المرحلة الثامنة: سجل العمليات والمراقبة المركزية

أضيف سجل مركزي جديد مستقل عن سجل تعديلات بيانات الطالب القديم. يسجل تغييرات قاعدة البيانات الفعلية التي ينفذها الموظف بعد تسجيل الدخول، ومنها إضافة وتعديل وحذف سجلات الطلاب والشؤون الأكاديمية والمالية والاستيراد وحسابات المستخدمين. كما يسجل إنشاء النسخ الاحتياطية اليدوية من الشاشة.

### البيانات المسجلة
- اسم حساب الموظف وقت تنفيذ العملية.
- القسم الذي تمت فيه العملية ونوع الإجراء.
- مسار الصفحة ورقم السجل المرتبط عند توفره.
- تاريخ ووقت العملية.
- عنوان IP الذي وصل منه الطلب إلى الخادم، ومعلومات الجهاز/المتصفح.
- طريقة الطلب HTTP ورمز الاستجابة.

لا يحفظ السجل كلمات المرور أو محتويات النماذج أو الملفات المرفوعة. ولا يسجل طلبات العرض GET أو إرسال النماذج التي لم ينتج عنها تغيير فعلي في قاعدة البيانات. إذا تم حفظ تغيير فعلي قبل ظهور خطأ لاحق، يسجل التغيير لأنه وقع بالفعل. التسجيل يبدأ من تاريخ تشغيل التحديث ولا ينشئ تاريخًا رجعيًا للعمليات السابقة.

### فتح شاشة السجل
- افتح /students/system-audit/.
- يمكن البحث باسم الموظف أو العملية أو مسار الصفحة أو رقم السجل.
- يمكن التصفية حسب القسم والفترة الزمنية.
- تعرض الشاشة 100 عملية في الصفحة مع إمكانية التنقل بين الصفحات.
- الشاشة متاحة لمدير النظام، ولمجموعتي مدير شؤون الطلاب ومراجع التقارير وفق الصلاحيات المحددة.

### حماية السجل
- سجلات العمليات للقراءة فقط من واجهة Django Admin؛ لا يمكن إضافتها أو تعديلها أو حذفها من لوحة الإدارة.
- لا تخزن بيانات النماذج الحساسة أو كلمات المرور.
- يعتمد عنوان الجهاز على الاتصال المباشر بالخادم (REMOTE_ADDR) ولا يثق تلقائيًا في ترويسة X-Forwarded-For التي يمكن تزويرها.
- إذا تعذر حفظ سجل العملية، لا يتسبب ذلك في إلغاء عملية الموظف الأساسية؛ يسجل النظام الخطأ في سجل تشغيل الخادم. لذلك يجب متابعة سجلات Docker ومساحة قاعدة البيانات دوريًا.
- هذه آلية مراقبة تشغيلية للطلبات الناجحة وليست سجل تدقيق جنائيًا مقاومًا للتلاعب من مسؤول قاعدة البيانات أو الخادم.

### بعد تحديث المشروع
نفّذ ترحيل قاعدة البيانات مرة واحدة بعد نشر الملفات:

    docker compose exec web python manage.py migrate

ثم تحقق من الصلاحيات وسجّل الدخول بحساب المدير لفتح شاشة سجل العمليات. إذا كانت الخدمة غير عاملة بعد تحديث الصور، أعد بناء الخدمات:

    docker compose up -d --build


## المرحلة التاسعة: مراجعة الأمان والتشغيل المتزامن

أضيفت تحسينات وقائية على إعدادات الخادم:

- يمنع التطبيق بدء التشغيل في وضع الإنتاج إذا بقي مفتاح Django الافتراضي أو كان المفتاح أقصر من 50 حرفًا.
- يمنع استخدام قائمة مضيفين فارغة أو wildcard في وضع الإنتاج.
- إعداد صريح لتفعيل HTTPS عبر `HTTPS_ENABLED=1`، ويؤدي ذلك إلى تفعيل تحويل HTTPS وملفات تعريف الارتباط الآمنة وHSTS. لا تفعّله على تشغيل LAN عبر HTTP إلا بعد إعداد شهادة TLS فعلية.
- إضافة `CSRF_TRUSTED_ORIGINS` اختياريًا، وعدم الثقة في ترويسة البروكسي إلا عند ضبط `TRUST_PROXY_SSL=1` خلف وكيل موثوق ينهي TLS.
- تحديد حجم ملفات الطلبات إلى 10 ميجابايت، وملفات Excel المستوردة إلى 10 ميجابايت.
- إعادة قراءة سجل الطالب وقفل صفه داخل معاملة قاعدة البيانات أثناء التعديل؛ هذا يقلل فقدان تحديثات الموظفين المتزامنين على PostgreSQL.
- لم تتم إضافة أي خدمة خارجية أو CDN إلى التشغيل؛ بعد تجهيز الحزم وصور Docker محليًا يظل الاستخدام اليومي ممكنًا دون إنترنت.

### إعدادات البيئة

- `HTTPS_ENABLED=0` للتشغيل الداخلي HTTP، أو `1` فقط بعد تجهيز HTTPS.
- `CSRF_TRUSTED_ORIGINS=http://192.168.1.10:8000` عند الحاجة، مع استبدال العنوان بعنوان الخادم الفعلي.
- `TRUST_PROXY_SSL=1` فقط عند وجود Reverse Proxy موثوق ينهي TLS.
- `SECURE_HSTS_SECONDS=31536000` عند تشغيل HTTPS فقط.

### اختبارات القبول قبل الاستخدام الرسمي

1. أنشئ `SECRET_KEY` عشوائيًا وفريدًا بطول 50 حرفًا أو أكثر، واضبط `ALLOWED_HOSTS` على عناوين الخادم المستخدمة فقط.
2. نفّذ `python manage.py check --deploy` بعد ضبط إعدادات الإنتاج وراجع التحذيرات.
3. نفّذ `python manage.py test students`، ثم اختبر بحسابين تعديل الطالب نفسه والتحصيل المتزامن على PostgreSQL اختبارية.
4. نفّذ استعادة كاملة لزوج النسخ (قاعدة البيانات وملفات media) على خادم اختبار، ثم طابق أعداد الطلاب والقيود والنتائج والإيصالات.
5. اختبر من جهاز موظف على LAN بعد فصل الإنترنت عن الخادم والعملاء، بعد تجهيز صور Docker والحزم مسبقًا.

**حدود الاختبار:** التغييرات البرمجية لا تثبت وحدها نجاح الاستعادة أو الأداء تحت حمل الموظفين؛ يلزم تنفيذ اختبار قبول على نسخة من قاعدة البيانات وبيئة LAN قبل اعتماد النظام رسميًا.


## المرحلة العاشرة: منع تعارض التعديلات وحماية التحصيل المالي

أضيفت حماية إضافية للبيانات دون تغيير حقول قاعدة البيانات أو إضافة migration:

- نموذج تعديل الطالب يحمل بصمة زمنية مخفية من وقت فتح الصفحة. عند إرسال النموذج، يقارن الخادم البصمة بآخر تحديث محفوظ داخل معاملة؛ إذا سبق لموظف آخر تعديل السجل، يرفض الحفظ ويطلب إعادة تحميل الصفحة ومراجعة البيانات الحالية بدل الكتابة فوقها.
- يظل قفل صف الطالب `select_for_update()` مستخدمًا أثناء الحفظ، وتُسجل التغييرات المقبولة في سجل التعديلات.
- عمليات تسجيل السداد وإلغاء الإيصال وإلغاء الاستحقاق تستخدم قفل الاستحقاق المالي بترتيب موحد داخل معاملة، حتى لا يجري إلغاء استحقاق بالتزامن مع تسجيل دفعة عليه في قواعد البيانات التي تدعم أقفال الصفوف.
- يعتمد منع تكرار رقم الإيصال على قيد `unique=True` الموجود بقاعدة البيانات، مع معالجة تعارض الإدخال وإظهار رسالة واضحة بدل خطأ خادم.
- بقيت قيود المبالغ الموجبة كما هي، ولا يسمح نموذج الإيصال بمبلغ صفري أو سالب.

### اختبارات المرحلة العاشرة

أضيفت اختبارات تغطي رفض نموذج طالب قديم بعد تحديث السجل، والسماح بالحفظ عند استخدام النسخة الحالية، ورفض رقم الإيصال المكرر، ورفض مبلغ السداد غير الموجب.

### ملاحظات تشغيلية مهمة

- لم تتطلب هذه المرحلة migration جديدة.
- أقفال `select_for_update()` تعتمد على دعم محرك قاعدة البيانات لها؛ PostgreSQL هو الاختيار الموصى به لتشغيل عدة موظفين بالتزامن. SQLite مناسب للتطوير والاختبار المحدود، ولا يوفر أقفال صفوف مكافئة.
- لا تمنع حماية النموذج موظفين من فتح الصفحة في الوقت نفسه؛ لكنها تمنع النموذج الأقدم من الكتابة فوق تعديل الموظف الآخر عند الحفظ.
- يجب اختبار التحصيل المتزامن عمليًا على PostgreSQL وبيانات اختبار قبل التشغيل المالي الرسمي. اختبارات Django وحدها لا تحاكي ضغط عدة أجهزة حقيقية أو ظروف شبكة LAN.


## المرحلة الحادية عشرة: استكمال حماية النسخ الاحتياطية

تمت مراجعة خدمة النسخ الاحتياطي القائمة وإصلاح نقطة تشغيل مهمة: كانت خدمة `backup` تصل إلى وحدة النسخ الاحتياطية وقاعدة البيانات، لكنها لا تشارك وحدة ملفات `media`؛ وبذلك قد تنتج النسخ المجدولة أرشيف مستندات فارغًا. أصبحت الخدمة الآن تقرأ وحدة `media_data` بوضع القراءة فقط، مع استمرار حفظ النسخ في `backup_data`.

كما أضيفت سياسة احتفاظ مزدوجة وآمنة:
- الاحتفاظ بالنسخ وفق عدد مجموعات النسخ عبر `BACKUP_RETENTION_COUNT` (الافتراضي 30 مجموعة).
- استمرار حد الاحتفاظ الزمني `BACKUP_RETENTION_DAYS` (الافتراضي 30 يومًا).
- تُعامل قاعدة البيانات وأرشيف المستندات كمجموعة واحدة، وتحذف الملفات التابعة للمجموعة معًا فقط.
- لا تحذف آلية التنظيف الملفات غير المعروفة أو الملفات التي لا تطابق نمط أسماء النسخ المعتمد.
- يمكن ضبط تكرار النسخ من `BACKUP_INTERVAL_SECONDS`: يوميًا `86400` ثانية أو أسبوعيًا `604800` ثانية.

### إعدادات النسخ
أضف أو حدّث القيم التالية في ملف `.env`:
```env
BACKUP_INTERVAL_SECONDS=86400
BACKUP_RETENTION_DAYS=30
BACKUP_RETENTION_COUNT=30
BACKUP_DIR=/app/backups
```

بعد التحديث أعد بناء الخدمات:
```bash
docker compose up -d --build
```

**اختبار قبول مطلوب:** أنشئ نسخة يدوية، وتأكد من وجود ملف قاعدة البيانات وملف `_media.tar.gz` بالحجم المتوقع، ثم اختبر استعادة الزوج على بيئة اختبار. لا تعتبر وجود ملفات النسخ وحده إثباتًا لاكتمال اختبار الاستعادة.
